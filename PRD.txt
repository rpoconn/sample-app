Context
At Daptic, we track regulatory alerts published by jurisdictions around the world:
US federal agencies, individual states, Canadian provinces, international
standards bodies, and more. Users can configure which jurisdictions they want to
monitor, organized as a hierarchy — regions contain countries, countries contain
states or provinces, and some go deeper to the city level.
Two levels of access shape what a user can configure.
First, each organization (a company that subscribes to Daptic) has a set of
jurisdictions it has paid for. A manufacturing company focused on the US might
have US federal and all US states, but not Canada or city-level coverage. These
are the jurisdictions available to everyone at that company.

Take-Home Project: Jurisdiction Settings 1

Second, within those organization-level entitlements, each individual user can
configure their own personal selection. A regulatory affairs manager focused on
California and New York can narrow their view to just those, while a colleague
tracking federal-only can do the same without affecting anyone else.
The feature you're building handles that second layer: personal configuration
within organization entitlements. Jurisdictions outside the org's plan should be
visible so users can see what exists, but not selectable.
This is one of the more UX-sensitive parts of the product. The hierarchy is deep
with a lot of jurisdictions (we are constrained to a smaller subset here but can get
up to thousands in production), and users have varying levels of granularity in
what they care about.

Part 1: MVP Implementation
What to build
A backend server and a TypeScript/React frontend that together let a user
configure their jurisdiction subscriptions.
The full functionality should:
Render the jurisdiction hierarchy and support selection at any level
Distinguish between jurisdictions the organization has paid for and those it has
not
Store and produce a clear output representing the user's current selection
(which jurisdiction IDs are active)
Be able to return the list of selected jurisdiction IDs (for another API to
potentially call)
Use whatever backend language and framework you're comfortable with. Keep
storage simple (in-memory or SQLite is fine), and skip real auth; passing a user ID
is enough.
How you model the data, design the API, manage state, and structure the code is
up to you, we’ll plan to discuss during the debrief.
